# 商城管理系统

一个**学习用途**的前后端分离商城系统，含**管理端**与**用户端**两侧，从零分 18 个里程碑搭起来。

它能走完一整条真实的交易闭环：

> 注册 → 浏览商品 → 加入购物车 → 填地址 → 下单 → 模拟支付 → 管理员发货（**填承运商 + 单号**）
> → 管理员补录物流轨迹（**录到「已签收」自动完成订单**）→ 确认收货 → 发表评价

---

## 一、这是什么 / 学什么

这个项目的目的**不是**做一个能上线的商城，而是**把一套完整的后端分层和 Spring 生态用法亲手走一遍**。

**学的是**（这三条是搭这个项目时明确的目标）：

- **理解分层与代码设计** —— Controller / Service / Mapper 各自该管什么，一条业务规则该在哪一层定义、在哪一层强制；
- **完整跑通一个系统** —— 不是零件演示，而是一个从建库到前端页面的闭环；
- **熟悉 Spring 生态用法** —— Spring Boot、Spring MVC、MyBatis、拦截器、AOP 式横切（全局异常处理）、定时任务。

**刻意不侧重**：SQL 与表设计。表结构讲解点到为止（13 张表都建了，但不追求复杂范式），因为这不是这个项目的学习目标。

**规模**（数字都是写这份 README 时当场数出来的）：

| 项 | 数量 |
|---|---|
| 后端 Java | 147 个文件 / 24,176 行 |
| MyBatis XML 映射 | 14 个文件 / 3,215 行 |
| 管理端前端 `mall-web` | 23 个源文件 / 6,907 行 |
| 用户端前端 `mall-shop` | 35 个源文件 / 13,157 行 |
| 测试与工具脚本（Python） | 约 18,600 行 |

> 合计约 5.2 万行。数量本身没有意义，列出来只是让人对体量有个概念。

**⚠️ 这份 README 只是目录和索引。** 这个项目里真正值钱的东西是散落在源码里的成段中文论证 ——

## 二、技术栈

| 工程 | 技术 | 端口 |
|---|---|---|
| `mall-server` | Spring Boot 3.5.16 · Java 21 · MyBatis (原生 XML) · MySQL 8 · Maven · Lombok | **8080** |
| `mall-web` | Vue 3.5 · Vite 8 · Element Plus 2.14 · Pinia 4 · vue-router 5 · axios | **5173** |
| `mall-shop` | 同上 | **5174** |
| 中间件 | MySQL 8.0（业务数据）· Redis（购物车） | 3306 / 6379 |

**几个选型理由**（都是刻意的，不是随手挑的）：

- **Spring Boot 3.5.16 而不是最新的 4.x** —— 3.x 的中文资料和排错答案远多于 4.x。
  对一个学习项目来说，**撞坑之后能搜到答案**比用上最新版更重要。
- **MyBatis 用原生 XML，刻意不用 MyBatis-Plus** —— 目的是看清 Mapper 层到底在做什么。
  MyBatis-Plus 会把 SQL 藏起来，而这恰恰是想学的部分（动态 SQL、`<foreach>`、`resultMap`、
  `useGeneratedKeys` 的边界……）。
- **购物车用 Redis 而不是 MySQL** —— 学习目的（想练缓存），同时也是合理的工程选择：
  购物车是高频读写的临时数据，用 Hash 存 `mall:cart:{memberId}`，30 天滑动过期。
- **登录态用 JWT 而不是 Session** —— 前后端分离下天然契合，服务端无状态。
  ⚠️ JWT 必须带 `type` claim（`ADMIN` / `MEMBER`）：`admin_user.id` 和 `member.id` 都可能等于 1，
  不带类型就能拿会员 token 冒充管理员。
- **`spring-security-crypto` 而不是 `spring-boot-starter-security`** —— 只需要 BCrypt 一个功能，
  引入整个 starter 会连带一整套自动配置的过滤器链，和本项目自己写的拦截器打架。

> ⚠️ **Redis 必须是名为 `mall-redis` 的容器。**
> ```bash

> ```
> 容器名不能随便改 —— 6 个测试脚本要用 `docker exec mall-redis redis-cli` 直连它清 key，
> 名字不对那些脚本会失败。这是一个真实且不显然的前置条件。

### 2. 建库

**全新安装**（库里什么都没有）：跑全量脚本 `sql/mall.sql`，它会建好 13 张表并塞入种子数据。

> ## ⚠️ `sql/mall.sql` 是 **DROP 重建**脚本
> 它会先 `DROP` 掉所有表再重建。**只能用于全新安装，
> 绝不要对一个已经有数据的库执行** —— 那会清空里面的一切。

**已有的库**（已经有数据，想让表结构跟上）：按顺序各跑一次增量迁移脚本：

```
sql/migration-08-order.sql
sql/migration-08b-idempotency-scope.sql
sql/migration-08c-shop-catalog.sql
sql/migration-08d-shop-catalog-2.sql
sql/migration-09-payment.sql
sql/migration-10-ship.sql
sql/migration-11-product-image.sql
sql/migration-12-review.sql
sql/migration-13-sku.sql
sql/migration-13b-sku-drop-columns.sql
sql/migration-14-category-tree.sql
sql/migration-14b-sku-price-tiers.sql
sql/migration-17-after-sale.sql
sql/migration-17b-order-freight.sql
sql/migration-18-logistics.sql
```

> ★ `18` 是**第四次应验「加列不影响任何现有代码」**：
> `orders.logistics_company` / `tracking_no` 都是 `DEFAULT NULL`，
> 而库里已有的 5 笔真实订单发货时根本没有这两列，`NULL` 就是它们的真值 ——
> 所以这个脚本**一条 `UPDATE` 都没有**，`mall.sql` 的种子区也一个字没改
> （前三次分别是 `parent_id` / `freight_amount` / `market_price`）。
>
> ⚠️ 用 `DEFAULT ''` 而不是 `DEFAULT NULL` 会毁掉这一点：
> 空字符串在 `if (company)` 里是**真值**，用户端会显示一行空白。
> 「还没发货」是**缺席**，不是值。

> ★ `17b` 是本项目里**最没有副作用的一次 schema 变更**：
> `orders.freight_amount` 是 `NOT NULL DEFAULT 0.00`，而历史订单本来就没收运费，
> `0.00` 就是它们的真值 —— 所以这个脚本**一条 `UPDATE` 都没有**，
> `mall.sql` 的种子区也一个字没改。这是「加列不影响任何现有代码」的**第三次应验**。
>
> ⚠️ 反过来说，`DEFAULT` 是会**静默吃掉忘记写的列**的：
> 如果 `OrderMapper.insert` 的列清单里漏了 `freight_amount`，INSERT 照样成功、
> 不报错不警告，只是运费永远是 0，而 `total_amount` 里含了运费。
> 挡住它的只有 `sql/test-after-sale.py` 里那条「实付 = 明细之和 + 运费」的断言。

> ⚠️ **`migration-13b` 是不可回滚的那一步，跑之前先 `mysqldump` 备份。**
> 它删掉 `product.price` / `product.stock` —— 那两列在里程碑 13 的阶段 2~5
> 以「派生汇总」的身份活着，也就是说**同一份数据有两个写入者**。
> 删掉它们才是那一轮要的东西本身（一个字段只能有一个定义者），
> 而不是"清理遗留"。**它的前面必须有备份，不是因为它危险，
> 而是因为跑完之后就没有那个列可以拿来对账了**（见第 11 节那段对账）。

> ### 补充：商品目录是怎么来的
> `08c` 和 `08d` 这两份**不是手写的**，是 `sql/gen-shop-assets.py` 生成的
> （一次产出商品图 `.svg`、迁移脚本、和 `mall.sql` 的种子片段）。
> 手抄 100 行 INSERT 和 100 个文件名，总有一天会把某个商品的封面配错，
> 而那种错误在页面上看起来完全正常 —— 只是画的是另一件商品。
> 要加商品，照 `PRODUCTS_BATCH_2` 的样子加一份新批次，再跑一遍生成器；
> ⚠️ 但 `08c` / `08d` 已经跑过、**已冻结**，生成器不会再改写它们。

> ### ★ 改动 schema 时，上面两份**都要改**
> - `mall.sql` 改它，是为了「新人拿到项目能一键建库」；
> - `migration-XX-*.sql` 改它，是为了「已有数据的库能跟上」。
>
> 只改一份的后果是**新人装的库和开发机的库悄悄分叉**，
> 而两份 `SHOW CREATE TABLE` 长得一模一样的时候，没有人会发现。
>
> ⚠️ 另外：DDL 里的 `COMMENT` 也是注释，但**它被存进了数据库**。
> 改 `.sql` 文件只影响以后新建的库，已经建好的库里那份仍是旧的
> （`SHOW FULL COLUMNS` 和 `mysqldump` 都会把它导出来）。**两处都要改。**

**★ 为什么按 URL 前缀把 Controller 分成 `admin` / `shop` 两个包？**

因为两边**能看到的数据和权限完全不同**：管理端能看所有会员的订单，用户端只能看自己的；
管理端能改商品，用户端只能读。混在一个包里会变成一堆 `if (isAdmin)`，
而且**没法按路径一刀切加拦截器** —— 而现在 `AdminAuthInterceptor` 拦 `/api/admin/**`、
`MemberAuthInterceptor` 拦 `/api/shop/**`，各管各的，一行路径通配就够了。

其余几层的说明，见各包下的类注释。

## 六、权限边界

**认证方式**：JWT 放在 `Authorization: Bearer <token>` 请求头里，由两个拦截器校验。

| 路径 | 要求 |
|---|---|
| `/api/admin/**` | 管理员 token（`type = ADMIN`） |
| `/api/shop/**` | 会员 token（`type = MEMBER`） |
| `/uploads/**` | **公开，无鉴权** |
| `/api/health/ping` | 公开（不在任何拦截器的路径范围内） |

**被排除在鉴权外的匿名路径共 7 条**（原文照抄自 `WebMvcConfig`）：

```
/api/admin/auth/login          ← 管理端唯一一条

/api/shop/auth/register        ← 注册完即登录，本来就还没有 token
/api/shop/auth/login
/api/shop/products             ← 游客可浏览商品
/api/shop/products/**          ← 含商品详情、商品评价列表
/api/shop/categories           ← 游客可按分类筛选
/api/shop/skus/**              ← 规格读取（里程碑 15 阶段 3 新增，见下）
```

> ### ⚠️ 这张清单是**人工维护**的，而路径匹配是**自动**的
> 两者一旦不同步，后果是**要么把该保护的接口公开出去，要么把公开接口锁死**，
> 而且都不会报错。**新增一棵匿名可读的路径树时必须回来补一行**
> —— 只往已有的树里加接口是自动的，新开一棵永远不是。
>
> 这条规矩在里程碑 15 身上应验了一次，而且是**反面**的：
> SKU 读取接口挂在一棵新树 `/api/shop/skus/**` 上，一个字都没沾到这份清单，
> 于是拦截器把它当成要登录的接口 —— 测试当场拿到 401。
> **注意这次清单并没有「说假话」，它什么都没说**：权限照旧生效，只是生效成了错的那一种。
>
> 反过来的一条是**红线**：**上传接口必须挂在有鉴权的路径树下**。
> `POST /api/admin/images` 和 `POST /api/shop/images` 都要求登录 ——
> 挂错地方等于任何人都能往服务器上写文件。
>
> ★ 一个反直觉的例子：`ShopReviewController` 类前缀是 `/api/shop`，
> 它里面 `GET /api/shop/products/{id}/reviews` 因为**落在排除树的覆盖范围内**而匿名可读，
> 而 `POST /api/shop/reviews` 落在一条**全新的、没被排除的**路径树里所以必须登录。
> **同一个类里两个方法权限不同 —— 决定权在这个配置里，不在那个类里。**
>
> ★ 那 `/api/shop/skus/**` 凭什么匿名？判据不是「现在有没有游客调它」（暂时没有），
> 而是**它泄露的东西是不是已经匿名可得了**：它返回的每个字段，
> 商品详情接口原样都返回，所以放开它的**新增**泄露是零。
> 哪天有人往这个响应里加了详情接口没有的字段（成本价、真实进货量），这条理由就作废了。
>
> ### ✅ 这句话在里程碑 16 到期了 —— 而理由**没有**作废
>
> 16 轮真的加了成本价，加的位置正是那句话点名的那个方向。做法是把边界放在 **VO** 上：
>
> ```text
> product_sku.cost_price       ← 一个真实的列，SQL 该查就查（ProductSkuMapper 的列清单里有它）
>         ↓
> SkuVO            公共字段：id / specs / specText / price / marketPrice / stock
>  ├─ ShopSkuVO   （用户端）—— 到此为止
>  └─ AdminSkuVO  （管理端）—— 加 costPrice / grossMargin / grossMarginPercent
> ```
>
> **`/api/shop/**` 一个字段都没变**，所以这条理由仍然成立。
> 但「成立」不能靠自觉 —— 现在有两处守着它，而且是**双向**的：
> `sql/test-price.py` 的 E 组（扫 192 个键名，一个都不许含 `cost` / `margin`）
> 和 `sql/test-frontend-contract.py` 里同名的三条加一条反空转守卫。
>
> ★★ 为什么必须是双向的，值得记牢：
> **只有「用户端不许有」时**，成本三件套整个没实现也是一片全绿；
> **只有「管理端必须有」时**，把 `costPrice` 加到父类 `SkuVO` 上——一行改动、
> 零编译错误、不用登录就能读——**也照样全绿**。
> 两条互为对方的空转守卫，拆开任何一条都会变成一条不会红的检查。
>
> ⚠️ 而危险恰恰在父类那一侧：`ShopSkuVO extends SkuVO`，
> 「往公共字段里加一个」和「往管理端字段里加一个」在代码上只差一行，
> 在后果上差一个匿名泄漏。

**★ 为什么 `/uploads/**` 是公开的？**

因为 `<img src="...">` 发不出 `Authorization` 请求头。图片要么公开，要么就得把 token 塞进 URL
（那更糟）。商品图本来就该公开，所以这不是漏洞，是权衡后的选择。

## 七、18 个里程碑

每一轮都要求**可运行、可验证**，而不是「写完就算」。表里记的是那一轮**真正学到的东西**。

| # | 里程碑 | 这一轮的知识点 |
|---|---|---|
| 1 | 骨架 + 建库建表 | 分层骨架、统一响应体、连上数据库 |
| 2 | 商品 CRUD 全链路 | 讲得最细，作为后续所有功能的模板 |
| 3 | 分类管理 + `/api/admin` 前缀改造 | 路径前缀作为权限边界 |
| 4 | 管理端登录 + JWT + 拦截器 + 路由守卫 | 前后端如何各自守住「未登录不能进」 |
| 5 | 用户端工程 + 会员注册登录 | 第二套拦截器；JWT 的 `type` claim 为什么是必需的 |
| 6 | 商品浏览（列表 / 详情 / 筛选 / 搜索 / 排序） | 匿名可读的边界划在哪；筛选条件放进 URL |
| 7 | **购物车（Redis）** | 缓存的数据结构选择；**只存 id 和数量，价格永远现查** |
| 8 | **下单流程** | 事务、`UPDATE ... WHERE stock >= ?` 的影响行数、价格快照、幂等键的作用域 |
| 9 | **模拟支付 + 取消 + 超时自动取消** | **两条条件 UPDATE 就是并发防护本身**；顺序反过来会让库存凭空翻倍 |
| 10 | 我的订单 + 管理端订单管理 | 状态机闭环；**确认收货绝不归还库存**（和取消恰好相反） |
| 11 | 商品图片上传（多图图集） | 魔数校验而非信任文件名；**图集的三态 `null` / `[]` / `[...]`** |
| 12 | 商品评价 | **一条不变量交给数据库**（`UNIQUE KEY`）而不是 Service 里的查重 |
| 13 | 收尾：统一异常完善 + README | 协议错误与业务结果的边界；一条只在注释里的规则等于没有规则 |
| 14 | 清账：金额显示收口 + 注释纠偏 | **同一个事实有两份实现，就一定会分岔** —— 清出 4 份 `toFixed(2)` 副本 + 4 处裸渲染 |
| 15 | **商品多规格（SKU）** | **一个字段只能有一个定义者**；`spec_json` 的规范化是唯一索引的前提；**语义变了的数据不能迁移，只能作废** |
| 16 | **分类多级 + 价格体系（划线价/区间/成本毛利）** | **「加列」不影响任何现有代码**（第二次应验，这次连种子区都一个字没改）；**一个显示出来的值，必须由它旁边的那两个输入算出来**；**「取不到」和「本来就没有」在界面上长得一模一样** |
| 17 | **售后（仅退款 / 退货退款）+ 运费** | **「按行的售后」对「按订单的状态」** —— 同一个不对称在本轮出现四次，每次的解法都是「行级事实存在行上、聚合只在唯一一处」；`active_token` 让「同时只能有一张进行中的售后单」变成唯一索引能看见的事；**库存归还只能挂在 `status → 3` 那一条 UPDATE 的影响行数上**；运费的 `DEFAULT 0.00` 会静默吃掉忘记写的列 |
| 18 | **物流（承运商 + 单号 + 手工轨迹）** | **「外部世界的记录」对「系统内部的状态」** —— 前者可以独立存在，后者绝不能被前者*猜*出来（所以签收联动靠 `status == SIGNED` 这个码，不是靠描述里的中文）；**同一条边第一次有两个行动者、两条 SQL**（「已发货 → 已完成」既有买家确认收货、也有管理员录签收，和「取消」那条边同一个形状）；**断言的方向由「条件是充要还是充分」决定**（签收 ⇒ 已完成 单向成立，反过来是正常路径）；**补录是轨迹的默认用法，所以排序键不能是 `id`** |

★ 标出的几轮是全项目技术含量最高的部分。

> ★★ **第 16 轮没有新增任何一条接口路径。** 它改的都是**已有接口的形状**：
> `GET /api/admin/categories` 从分页列表变成整棵树，商品列表/详情多了 `maxPrice`，
> SKU 多了 `marketPrice` / `costPrice` / `grossMargin` / `grossMarginPercent`。
> 所以下面「18 个 / 29 个」两个数字一个都没变 ——
> **接口数量和接口契约是两件事，这一轮加的全部是后者。**
> 而契约变化恰恰是**最不会报错**的那一类改动：字段多一个少一个，
> 后端所有测试照旧全绿，只有前端会安静地渲染出一片空白或者一个「未设置」。
>
> ★ **第 17 轮反过来：它加了 8 条路径**（用户端 4 + 管理端 4），
> 所以下面那两个数字变成了「22 个 / 33 个」；同时它又**改了契约** ——
> `orders` 的响应多了 `freightAmount`，`totalAmount` 的语义从「商品小计之和」
> 变成了「实付金额（含运费）」。**两件事在同一轮里都发生了。**
>
> ★ **第 18 轮两件事都是**：加了 4 条物流路径（管理端 3 + 用户端 1，
> 于是「25 个 / 34 个」），**并且改了发货接口的契约** ——
> `POST /api/admin/orders/{orderNo}/ship` 从「没有请求体」变成
> 「**必须**带承运商和快递单号」。
> 这一处契约变更值得单独记一笔，因为它有一个人人都会猜错的形态：
> **旧后端会静默忽略多传的请求体**（没有 `@RequestBody` 就没有反序列化，
> 多传的 body 被扔掉，接口照常 200）。所以「加了必填字段」这件事
> **在旧代码上不会自己暴露** —— 唯一的见证是「不带 body 必须 400」。

**几个值得单独拎出来的设计**：

- **订单明细存价格和商品名快照**，不是每次 `JOIN` 商品表取现价 ——
  因为商品会改价、会下架、会被删，而历史订单必须永远显示当时的价格。
  里程碑 15 又给它加了第三样快照：`sku_spec`（当时买的是哪个规格）。
- **扣库存用 `UPDATE product_sku SET stock = stock - ? WHERE id = ? AND stock >= ?` 判断影响行数**，
  不是「先查够不够再改」。后者在并发下必然超卖。
- **支付的幂等不需要幂等键**。下单的副作用是「新增一行且能无限新增」，所以要键；
  支付的副作用是「把一行从 A 推到 B」，`WHERE status = 0` 第二次天然拿到 0 行。
  **当「目的状态已经达成」可以被检测出来时，就不需要额外的幂等键。**
- **有些不变量只有数据库能真的保证**。「一条订单明细只能评一次」写在 Service 里挡不住并发
  （两个请求可以同时查到「没评过」），所以它是一个 `UNIQUE KEY`。
  里程碑 15 的 `uk_product_spec (product_id, spec_json)` 是同一个理由的第二次应用。
- **★ 里程碑 15 那条最贵的教训：「加一列」不影响任何现有代码，「收紧约束」必然影响。**
  迁移脚本因此拆成了两步（`migration-13-sku.sql` 只加不删 / `13b` 才删列、才 `DROP DEFAULT`）。
  第一版把 `DROP DEFAULT` 写进了 13，跑测试时**每一次下单都 500**（`ERROR 1364`）——
  因为当时 Java 侧的 `batchInsert` 列清单里还没有那一列。**它不静默，但会被误读成「迁移把系统搞坏了」。**
- **★ 价格和库存的唯一真源是 `product_sku`。** `product` 表上不汇总一份库存 ——
  汇总列就是第二个写入者，而库存在事务里被并发扣减，汇总必然漂移，
  这个项目有 20 线程并发抢库存的测试，漂移一定被测出来。

## 八、接口一览

统一约定：**业务结果返回 HTTP 200 + `body.code`；协议错误（路径、方法、报文格式不对）
返回真正的 HTTP 状态码。**

响应体形状：

```json
{ "code": 200, "message": "success", "data": { } }
```

> ⚠️ Jackson 配了 `default-property-inclusion: non_null` —— **值为 `null` 的字段会直接从 JSON 里消失**，
> 不是变成 `null`。前端读到 `undefined` 时，要先想清楚是「本来就没有」还是「后端漏给了」。

`code` 的取值：`200` 成功 · `400` 参数/协议问题 · `401` 未登录 · `403` 无权限 ·
`1001`~`1014` 业务错误 · `500` 服务端异常。

> 里程碑 16 新增的三个（全在分类树上）：
> `1009` 分类层级不合法（自己挂自己 / 挂到二级分类下 / 自己有子分类还去挂别人）、
> `1010` 上级分类不存在或已禁用、`1011` 分类下还有子分类，不能删。

> 里程碑 17 新增的三个（全在售后链路上）：
> `1012` 这条明细已有进行中的售后（撞了唯一索引）、
> `1013` 这条明细已退款（不能再申请 / 不能再评价）、
> `1014` 超过售后申请期限。
>
> ★ **业务码不分段，这是决定、不是还没做。** 「按模块分段」（比如
> 2xxx 给售后、3xxx 给物流）看起来更整齐，但它要求**整个区间重排**，
> 而已经发出去的码不能改（`1002` 永远是 1002）。在半途分段的结果是
> 订单相关的码一半在 1xxx、一半在 2xxx，**比分段之前更难查**。
> 分段唯一的收益是「看码就知道归属」，半途分段把这个收益也抵消了。
> **如果重来一次，应该在建 `ResultCode` 的那一轮就把分段定死。**
> 完整的三条理由写在 `ResultCode` 的类注释里。
>
> ★★ **里程碑 18（物流）兑现了这句话：本轮新增 0 个业务码，`ResultCode` 仍然止于 `1014`。**
> 这是**结论、不是遗漏** —— 物流的每一种失败都能用已有的码说清楚：
> 给未发货/已退款的订单录轨迹用 `1002`，订单或节点不存在用 `1003`，
> 而「承运商/单号/说明填得不对」走 `@Valid` 参数校验（`400`），
> 这是项目既有的分层（参数校验走 400，业务失败走业务码）。
> **这句话写在这里，是为了让下一个人不必重新论证一遍「是不是该用 3xxx」。**

> 判断恒为 false，用户端的「查看物流」入口**永远不显示**。这是同一个坑的**第 5 次**。
> ★ 唯一的例外是 `traces`：它**永远是数组**（没节点时是空数组），所以 `v-for` 不用判空。
>
> ★ **为什么用户端的物流接口也必须带 `member_id`**：物流里含
> **收货地址级别的隐私信息** —— 快件到了哪个城市、哪个网点、什么时候派送，
> 拼起来就能推出一个人住在哪一片。这比「订单金额」更敏感，
> 所以它的 SQL 和订单详情一样带 `WHERE member_id = ?`，
> 查别人的返回 `1003`（和「订单不存在」合并，不泄露「这个订单号是存在的」）。

> ★★ **上表里凡是提到价格的，说的都是「给人看的价」。**
> 用户端这几个商品/规格接口的响应里**没有任何 `cost` / `margin` 字段**，一个都没有 ——
> 这不是「暂时没加」，它是**边界**，而且有双向的断言守着（见第六节那段）。

## 九、测试怎么跑

测试脚本都在 `sql/` 下，**用标准库 `urllib` 手写，不依赖 `requests`**，
每个脚本独立可跑、自带清理。跑之前三个服务必须在运行。

```bash
cd sql
/d/python/python.exe test-order.py       # 或者你本机的 python
```

- 输出 `结果：N 通过 / M 失败`，**失败时进程退出码是 1**（可以直接串进 CI）。
- 脚本之间**不共享代码** —— 公共辅助函数是复制过去的，不是 import 的。
  这样任何一个脚本都能单独跑、单独改，不会因为动了公共库而连带影响别的脚本。

> ### ★ `test-sku.py` 里最贵的一条，是一个**动态证明 + 静态读源码**的组合
> 「同一件商品换了规格之后必须换幂等键」这条规则，**在 HTTP 报文里完全看不出来**：
> 用同一个键提交「黑色」再提交「白色」，后端分不出来，它只会把上一单原样返回 ——
> 接口 200、跳转成功、金额不对。所以那个脚本做两件事：
> 先用两个真实请求把「后端确实分不出来」这件事**演一遍**（断言只有一笔订单、且返回的是上一笔），
> 再**读出 `checkoutIntent.js` 的源码**断言签名里算了 `skuId` 而不是 `productId`。
> 这是第一次有脚本去打接口之外的东西来守住一条规则。
>
> ⚠️ **不写「恰好 N 项」**。脚本改过之后，这个数字立刻就旧了。
> 看真实数字就自己跑一遍 —— 那是唯一不会过期的来源。

**★ 四类脚本问的是四个不同的问题**：

- 前 16 个 `test-*.py` 问的是「**后端行为对不对**」；
- `test-frontend-contract.py` 问的是「**前端的假设对不对**」——
  接口返回的字段名前端读得到吗？前端发的 body 后端收得下吗？
- `test-frontend-format.py` 问的是「**前端的写法对不对**」——
  金额有没有走那唯一一份格式化函数。**它读源码，不打接口。**
- `test-schema-sync.py` 问的是「**`mall.sql` 和这张真实的库对不对得上**」——
  也不打接口，它读 `mall.sql`、查 `information_schema`，然后逐列比。

后三者存在的理由不一样：

`test-frontend-contract.py` 针对的是**前端没有类型检查**。字段名写错只会得到 `undefined`，
构建不报错、ESLint 不报错、页面也未必立刻崩 —— **这类 bug 只有契约测试能提前发现。**

`test-frontend-format.py` 针对的是一件更窄但更绝对的事：
**有些修复在 HTTP 报文里一个字节都看不见**。里程碑 14 修的是「拿到数字之后怎么印」，
接口返回的 JSON 完全没变 —— 所以那 12 个打接口的脚本**全都证明不了它修好了**。
能守住它的只有两样：这个脚本，和浏览器里肉眼看到的那个数字。
（那个脚本的 docstring 把这件事写全了，值得一读。）

`test-schema-sync.py` 针对的是**这个项目自己定的那条约定**（第 3 节「两份都要改」）。
它和上面那个是同一个形状：**改动本身没问题，只是有一份副本没跟上。**
这类 bug 的可怕之处在于**症状出现在离改动最远的地方** ——
漏改 `mall.sql` 时，老库早就被迁移脚本改过了，所以接口、测试、页面**全是绿的**；
撞上它的是几天后照 README 建库的新人，而他会先怀疑自己的 MySQL 版本。
★ 它是里程碑 16 加 `parent_id` 时现写的，**写完当场抓到自己一次**。

> ### ★ 一个提醒：警惕「占位断言」
> 早期里程碑里写过一些「某接口 → 404（因为 Controller 还没做）」的断言。
> 它们测的其实是**当时的实现进度**，而不是业务规则 —— 里程碑推进后必然失败。
> 看到这类失败，先问「它是不是在测进度」，再决定改代码还是改断言。

> ### ★★ 一个没有断言的清理逻辑，等于没有清理逻辑
> 里程碑 15 阶段 6 收尾时数了一遍库，发现 `orders` 比它应有的样子多了 90 笔，
> 全部指向**已经不存在的会员**，`member_address` 多 33 条，同一个来源。
>
> 根因只有一行 —— `test-sku.py` 的 `main()` 里两行的顺序写反了：
>
> ```python
> member_setup()   # 先注册一个会员
> cleanup()        # 再把它删掉  ← 而 cleanup 的最后一句正是「删会员」
> ```
>
> `cleanup()` 删订单用的是 `DELETE o FROM orders o JOIN member m ON m.id = o.member_id
> WHERE m.username LIKE 'skutest%'` —— 这个写法有个**隐含前提：那个会员行还在**。
> 会员行被自己删掉之后，这三条 join 从此永远匹配 0 行：
> **删掉了会员，却把它的订单、明细、地址全留在了库里，一句错都不报。**
>
> **它能藏十几轮，靠的是三件事同时成立**：
> 1. 155 条断言全在问「接口做了它该做的事」，**没有一条在问「脚本自己有没有留垃圾」**；
> 2. JWT 认证**只验签名、不查库**，所以一个已经不存在的会员照样能下单、能取消、能看购物车 ——
>    C/D/E 三组整个是在一个**幽灵会员**名下跑完的，全部通过；
> 3. 症状（库里多几行）和断言（HTTP 200 + 业务码）在**两个不同的层面上**，谁也不会提醒谁。
>
> **修法两处**，缺一不可：
> - `cleanup()` 增加「**按 id 删**」：`DELETE FROM orders WHERE member_id = ？`。
>   用户名那条线索在会员被删之后**就永久失效了**（找不回一个不存在的用户名），
>   可靠的那条线索是 id —— 它在注册时就拿到了，不依赖会员行是否还在。
> - `main()` 改成 `cleanup()` → `member_setup()`：先扫上一次的残留，再注册本轮的会员。
>
> 然后再补上**第 3 件事：一条断言**。脚本末尾新增 `junk_snapshot()`：
> 跑之前和跑之后各数一遍「**无主行**」（明细找不到订单 / 订单找不到会员 / 地址找不到会员 /
> SKU 找不到商品 / 残留的测试商品），两者必须**一模一样**。
>
> ★ 为什么数「无主行」而不是行数：行数是会变的（真人也会下单），**无主行不会** ——
> 一个正常的库，孤儿永远是 0。这条断言在修之前会红，在修之后才绿，
> 而它才是这一类 bug **唯一**能被自动发现的地方。
>
> ⚠️ 已经攒下的那 90 笔订单 / 33 条地址的会员行早就没了，**按用户名再也找不回来**，
> 只能按 id 逐条清（`/tmp/mall-backup/orphan-*.tsv` 里有备份，id 也在旁边）。
> 这条不是「顺手改了别人的东西」，是**这次泄漏自己的残骸**。

## 十一、已知的取舍 / 明确不做的事

这一节比它看起来重要：**知道一个系统不做什么，和知道它做什么一样有用。**

| 不做 | 为什么 / 代价 |
|---|---|
| **不加数据库外键** | 加外键之后「删商品」会变成一条可能失败的语句，而约束拦下来的错误只能翻译成一句「系统繁忙」。**代价**：删除顺序必须自己守（晒图 → 评价 → 图集 → **SKU** → 商品），反了会留下孤儿行而且不报错。测试里有专门找孤儿的断言。 |
| **JWT 签发之后无法主动失效** | 服务端**只验签名，不查库**。所以一个已经被删掉的会员，手里那枚 120 分钟内的 token 依然全通：能下单、能取消、能看购物车。**代价**：没有真正的「登出」和「被踢下线」，要做到只能加黑名单或退回有状态会话。**这一条是被一个真实的 bug 逼出来的** —— 见「测试怎么跑」里那次幽灵会员：脚本把会员删了，却用他的 token 跑完了三组用例，全程绿。 |
| **`product` 表上不存价格，也不存库存** | 价格和库存的唯一真源是 `product_sku`（无规格的商品也有一条 `spec_json = '[]'` 的默认 SKU）。**为什么不留一份「汇总库存」**：汇总列就是第二个写入者，而库存在事务里被并发扣减，汇总必然漂移 —— 这个项目有 20 线程并发抢库存的测试，漂移一定会被测出来。**代价**：列表页的 `minPrice` / `totalStock` / `skuCount` 是一次 `GROUP BY` 派生表算出来的，100 件商品规模下可忽略，商品量大了要翻案。 |
| **「保存商品」= 全量覆盖 SKU 库存** | 管理端编辑页保存时提交的是每行的绝对库存值。**代价**：运营打开编辑页时库存 10，期间卖掉 3 件，他一保存库存就回到 10 —— **凭空多出 3 件**，而且两端都显示成功。**真正的修法是「库存调整走增量 ±N」**（单独的接口），明确推迟。当前的处理是在表单上写一行提示 + 记在这里。 |
| **「每个规格最多买 99 件」做不出「每件商品合计 99 件」** | 购物车的 Redis field 从 `productId` 换成了 `skuId` 之后，「这件商品一共加了多少件」不再 O(1) 可得。99 只能是**每个规格各自 99**。 |
| **不做规格级图片 / 规格级上下架 / 动态可选性** | 规格级图片要 `product_image` 加 `sku_id`，是独立的一块；「这个组合不生产」用 `stock = 0` 表达、前端标灰就够；「选完颜色某些尺码变灰」是动态可选性，只做了静态可选性（某个值在任何 SKU 里都不出现才标灰）。 |
| **分类最多两级** | `parent_id` 要么是 0，要么指向一个自己也是 0 的分类 —— **三级会被明确拒绝（1009），不是静默截断**。为什么不让它更深：前端只画两级（顶部导航 → 左侧栏），第三级**在商城页根本渲染不出来**，商家在后台建了「手机 → 手机壳 → 硅胶壳」，用户端只看得到前两级，**没有任何地方会报错**。加一级要同时改后端规则、两端渲染和测试，是独立的一轮。**代价**：分类目录没法再细分一层。 |
| **列表卡片上的划线价只在单规格商品上出现** | `MIN(price)` 和 `MIN(market_price)` **可以来自两个不同的 SKU 行**，直接并排显示就会渲染出一个**不存在的折扣**（「¥4999 ~~¥8999~~」，而 ¥8999 是另一个规格的原价）。所以商品级的 `marketPrice` 由 `CASE WHEN sku_count = 1` 这把锁挡着，多规格商品压根没有这个键。**多规格的划线价去详情页看** —— 那里用户选中了一个规格，那一行的原价是唯一确定的。 |
| **成本价只存在于 `AdminSkuVO`，毛利只在管理端详情** | 管理端**列表页不做成本/毛利列** —— 跨规格的「成本汇总」没有唯一答案（4 个规格成本 10/20/30/40，「这件商品的成本」是什么？），那是「经营看板」那一轮的事。**代价**：想知道一批商品的毛利，只能一件件点开。 |
| **商品表单里的毛利率是前端现算的预览，不是后端那个数** | 成本价输入框就在同一行、而且可以改。如果显示后端返回的 `grossMarginPercent`（那是**已经存进库的**价格算出来的），商家把成本从 70 改成 90 的那一刻，页面上就会写着一个**和旁边两个输入框对不上**的百分比。在「实时反馈」和「一份实现」之间选了前者，**代价**是两边各有一份毛利算法（`AdminSkuVO.of()` 和 `ProductForm.vue` 的 `marginPercentOf()`），舍入顺序必须一致，改一处要两处都改。 |
| **删记录不删磁盘文件** | 换图、删商品都不删已上传的图片文件。**代价**：磁盘只增不减。理由是把「数据库事务」和「文件系统」绑在一起不可靠。 |
| **评价不能改、不能删** | 业务上定成「一次定终身」。管理端只能整体删除（删掉后那条明细可以重评）。 |
| **不做真实支付 / 物流** | 范围外。支付是模拟的（点一下按钮就成功），没有第三方对接。 |
| **不做秒杀 / 优惠券 / 分布式 / 微服务** | 范围外 —— 这个项目要学的是分层和框架用法，不是分布式。 |
| **不做图片压缩** | 上传只做大小上限（2MB）和格式白名单，不缩放。 |
| **不做三级省市区联动** | 地址的 `region` 就是一个普通文本框。**代价**：地址格式由用户自己保证。 |
| **不做限流 / 配额** | 没有防刷机制。 |
| **SVG 不允许上传** | 虽然它是图片，但能内嵌 `<script>`，是最经典的图片 XSS 载体。白名单只放 PNG / JPEG / GIF / WEBP。 |
| **`test-exception.py` 不搬运已有脚本的断言** | 现有的协议错误断言（散在 `test-review` / `test-upload` / `test-shop-product` 里）一个字都没动。「顺手改掉别人依赖的东西」是协作里最招人烦的一类改动。新脚本测的是**状态码矩阵**（系统性的表），旧断言是**偶然碰到的一例**，两者不是重复。 |
| **分类只能通过「上级分类」选择器改父，没有拖拽** | 拖拽排序 / 拖拽改父是纯前端交互的大件（拖拽库 + 落库顺序 + 并发下的重排），排序仍用 `sort` 数字。分类也没有图标 / 图片 / SEO 字段 —— 这一轮 `category` 只加了 `parent_id` 一列。 |
| **删分类不级联、不迁移商品** | 下面还有子分类 → 1011；下面还有商品 → 1004。**都拒绝并说明原因**，不自动把商品挪到父分类、也不连带删掉子分类。理由和「不加外键」是同一种态度：**让用户看见「这里挂着东西」，而不是替他决定那些东西该怎么办**。 |
| **订单、购物车、结算页里不出现划线价** | 那三个页面只该出现**应付金额**。订单记的是「你付了多少」（它存的是价格快照），划线价是**展示**；把历史原价也快照进去，只会在对账的时候变成噪音 —— 而且它马上就会有第二个定义者。 |
| **不给现有 100 条 SKU 回填划线价 / 成本价** | 那是**发明数据**：给用户手工录入的 5 件商品编一个「原价」和「进价」，等于往这两个字段里灌一个它们从来没有过的含义。所以迁移只加列、不回填，库里那两列**全是 `NULL`**。**代价**：商城页一条删除线都没有、管理端毛利率全是「未设置」—— **这是正确的**，要看效果用 `tools/fixture-price.py` 造，验完删。 |
| **不做会员等级价 / 秒杀价 / 活动价** | 这一轮的价格体系只做「展示层」的四种价（售价、划线价、区间、成本）。**会员等级价是用户明确推迟的**，它要动的是下单时的定价（不只是显示），属于独立的一轮。 |
| **`total_amount` 的语义变了：从「商品小计之和」变成「实付金额」** | 里程碑 17 加了运费，`total_amount = 明细小计之和 + freight_amount`。**没有再加一列 `goods_amount`** —— 三个数之间会有两个等式要守，每一个都只能靠断言，**少一个列就少一条会漂移的边**。**代价**：「商品小计」只能靠 `total_amount - freight_amount` 算，而那是**减法**，`SUM(order_item.subtotal)` 是**加法** —— 同一事实的两份实现。挡住分岔的只有 `sql/test-after-sale.py` 里那条把两个方向摆在一起比的断言（它会同时抓住「`OrderMapper.insert` 忘了写 `freight_amount`」这个静默故障）。 |
| **`freight_amount` 是不可重算的快照** | 展示时永远读 `orders.freight_amount`，**绝不按当前规则重算**。理由和收货地址快照、成交价快照完全同类，而且更严重 —— 它是**涉及金钱的历史事实**。运营把包邮门槛从 99 降到 59 之后，一笔**已经付过 10 元运费**的历史订单会显示成「商品 ¥89 运费 ¥0 合计 ¥99」：运费 0 而合计 99，**两个数字自相矛盾**，且 `退款额 ≤ 实付额` 这条不变量也跟着错。全程没有任何一层会报错。 |
| **结算页不知道运费** | 加运费的那一刻起，`Checkout.vue` 上算的就不再是「应付金额」了。本轮的做法是**承认不知道**：那一处文案改成「商品合计」并注明「运费按下单时的规则计算」，权威数字在**下单之后的收银台**（那里读 `total_amount` + 一行运费）。**代价**：用户下单前看不到运费。**但它不会让人被多扣钱** —— 本项目的下单和付款是两步。★ **正解是加 `POST /api/shop/orders/preview`**（只算不写、与下单**共用同一个算钱函数**），本轮不做，记在这里。 |
| **不做「按比例分摊运费」** | 只有**整单退完**才退运费（判据是「每一行明细都有一张已退款的售后单」），部分退只退货款。分摊需要一条规则（按金额？按件数？按重量？）**没有唯一答案**；按金额比例会引入除法，除不尽时**所有行的退款额之和可能比运费多一分或少一分**。★ 另外「整单退」判的是**事后可验证的事实**，不是「用户勾选了全部明细」这个**意图** —— 勾了全部但只成功了一张，运费就退错了。 |
| **退款不真的动钱** | 只记金额（服务端算）+ 时间 + 去向（`refund_method` = 该订单 `pay_method` 的快照）。没有第三方对接、没有打款、没有对账文件。 |
| **先评价后退款的订单，评价会保留** | 退款**不删**已有评价，展示上也**不打「已退款」标记**。评价是用户当时的真实看法，退款不改变「他收到过这件商品并写过评价」这个历史事实。删掉会造成更坏的结果：**商品页的评分会因为一笔退款而悄悄变化**。退款只挡**新增**评价（`1013`）。 |
| **`active_token` 是本项目唯一的「同一事实两个表示」** | `after_sale.active_token` 和 `status` 说的是同一件事（这张单关没关）。它是被数据库能力逼出来的：MySQL **没有部分唯一索引**（`... WHERE status < 3`），而「一条明细同时最多一张进行中的售后单」必须由唯一索引来守（Service 里先查后写挡不住并发 —— 有血证）。做法是把「活跃」编码成唯一索引看得见的值：进行中 → `0`，已关闭 → **本行的 id**。**代价**：两个表示之间没有强制一致性，只能靠**两条方向相反的断言**守（「进行中的 `active_token` 必须是 0」「已关闭的必须不是 0」）。 |
| **不做售后单详情接口、不做 `after_sale_item` 明细表** | 前者：全部字段都在列表项里，加详情就是第二条装配路径。后者：一张售后单只对一条订单明细。**支持「整单退」靠的是 `orderItemIds: [...]` 一次建 N 张单**（一个事务，全成或全败），不是靠把 N 行塞进一张单 —— 那样「这条明细有没有活跃售后」会有**两个定义者**，而「运费退多少」也会失去唯一答案。 |
| **不做换货 / 维修 / 仅退货、不做「发货后 N 天自动确认收货」** | 售后只做用户拍板的两种类型。后面那条更重要：做了自动确认收货，`status = 2` 的订单就有了**售后时限起点**，而当前「没确认收货 = 不受 7 天时限约束」这条规则会变。 |
| **物流轨迹靠管理员手工录入，不对接任何快递公司 API** | 里程碑 18 的范围是「承运商 + 单号 + 手工节点」——**没有真实轨迹拉取**。所以线上库里一条轨迹都不会自己出现，`order_logistics` 是空的（**这是正确的**，要看效果用夹具造）。**代价**：轨迹的实时性和真实性全靠人；而反过来，**它是这个项目里唯一一处「系统记录的是外部世界发生的事」**，后半句才是这一轮真正学的东西。 |
| **不做部分发货 / 一张订单多个包裹** | 用户拍板单包裹。做多包裹会把「这单什么时候能确认收货」变成新问题（几个包裹都到了才算？先到的能不能先确认？），而 `orders.logistics_company` / `tracking_no` 这两列本身就是**订单级**的单值 —— 多包裹要动的是数据模型，不是加个字段。 |
| **录到「已签收」会把订单自动推到「已完成」** | 用户拍板。它落地的形状是**「已发货 → 已完成」这条边的第二个行动者**（`OrderAdminMapper.markCompletedByNo`，`WHERE status = 2` 和用户端那条一模一样），不是「订单状态多了一个写入者」—— 同一条边两个行动者两条 SQL，**「取消」那条边早就有先例**（用户主动取消 vs 超时取消）。★★ **不想要这个联动的话，删掉 `LogisticsServiceImpl.addTrace` 末尾那个 3 行的 `if` 即可，回退不是重做。** ⚠️ 但它有一个连带后果必须知道：自动完成会写 `complete_time`，而那是**售后 7 天窗口的起点** —— 相当于给这条时钟加了第二个起点。 |
| **删除轨迹节点【不】回退订单状态** | 删掉一条「已签收」，订单仍然是「已完成」。给它配一条回退 SQL 意味着**订单状态机第一次有了反向边**，而反向边的后果是「一张订单可以在已发货和已完成之间来回走」—— 所有依赖终态的逻辑（售后窗口、评价资格、`markShipped` 的闸门）都要重新论证一遍。⚠️ 这是**决定不是遗漏**，管理端对话框上写明了这一句。 |
| **轨迹只能新增和删除，不能修改** | 编辑一条节点 = 「从旧值改到新值」，它会引入「这一条到底发生过什么」的**两个版本**，而轨迹记录的就是发生过的事 —— **一条被改过的轨迹不是轨迹**。改错的做法是删了重录：这样 `create_time`（什么时候录的）和 `trace_time`（什么时候发生的）才是诚实的两个数。 |
| **不做「复制单号」按钮** | 它要多一个 `navigator.clipboard` 调用，而那个 API 在**非安全上下文**（http 且非 localhost）下会**静默失败** —— 用户点一下，什么都没发生，也没有提示。收益是省一次拖选。 |
| **物流没有启用 3xxx，`ResultCode` 仍然止于 `1014`** | 见第八节 —— 这是**兑现「不分段」**，不是拖延。 |

> ### ★ 「汇总库存一定会漂移」这句话，这里有一份实测证据
>
> 迁移期间 `product.price/stock` 被留下来当回滚预案，由管理端保存时**按 SKU 汇总回写**。
> 于是同一个事实暂时有了两个写入者 —— 而**它真的分岔了**：
>
> ```
> 商品 683「佳能 EOS R50 微单套机」   product.stock = 29    product_sku.stock = 30   ← 差 1
> 全库 100 件商品里，只有这 1 件对不上
> ```
>
> 分岔的过程可以逐条对上，**而且每一步单独看都是"对的"**：
> 种子里两个值都是 30（`sql/mall.sql` 的 SKU 种子段）；21:57 有一笔订单下单，
> 那时下单路径还在扣 `product.stock`（里程碑 15 阶段 4 之前），于是它变成 29；
> SKU 那一行是阶段 1 回填的，之后没人动过，还是 30。
>
> **值得记住的不是"差了一个数"，而是这件事的性质**：
> 两个写入者各写各的，**没有一方报错、没有一条日志、也没有任何接口能看出来** ——
> 我是拿一句 `p.price <> s.price OR p.stock <> s.stock` 主动去比对才发现的，
> 而且它甚至解释不了自己是**什么时候**变的（那笔订单的 `sku_id` 是 NULL，
> 按新模型它根本不会去动任何 SKU 行）。
>
> 结论就是本节第二行那条不变量：**一个字段只能有一个定义者。**
>
> ### ★★ 而删列【没有】修好这条数据 —— 这一点必须写清楚
>
> 阶段 6 删掉那两列之后，29 这个数不存在了，剩下的 30 成了唯一答案。
> 看起来"问题解决了"，但**真正被解决的是"能被发现"，不是"数据是对的"**：
>
> ```
> 那笔订单（order 913，已付款 4799.00）真的卖掉 1 台，
> 而这台相机现在的库存显示 30 —— 多算了一件。
> ```
>
> 删列只是**把分歧定格在其中一个值上**，然后让它再也无法被观察到。
> 如果那 1 件是最后一件库存，这条差异就是"超卖一件"。
>
> ★ 所以正确的顺序本来是**先对账、再删列**：
>   1. `p.price <> a.mn OR p.stock <> a.sm` 找出所有对不上的行（当时只有 1 件）
>   2. 逐条判断哪个值是真的（这里显然是 29 —— 订单在库、库存就该少 1）
>   3. 把那 1 行改对，让两个值一致
>   4. 再删列
>
> ### ★ 后来补做了第 3 步（2026-09-24，用户拍板）
>
> 删列时**没有做第 3 步**，因为它是"改用户库里的真实数据"，属于要显式拍板的事 ——
> 于是它先是作为一条已知的、量化的差异留在这里。用户拍板后已改对：
>
> ```sql
> UPDATE product_sku SET stock = 29 WHERE id = 52;   -- 商品 683 唯一的（默认）SKU
> ```
>
> 改之前先核对了三件事，缺一条都不能改：
> · 商品 683 只有这一条 SKU（`spec_json = '[]'`，`price` 4799.00），**不存在改错行的可能**；
> · order 913 是 `status = 3`（已完成）、`pay_time` 有值、`cancel_time` 为 NULL —— **真的成交了**，
> 它的明细 `quantity = 1`、`sku_id` 是 NULL（里程碑 13 之前下的单，按设计就该是 NULL）；
> · 那条明细上挂着 1 条真实评价 —— 顺带证明这单不是一个测试夹具。
>
> ⚠️ 这条 UPDATE 是**手工**执行的，不在任何迁移脚本里：迁移链重放不出来它
> （新建的库从一开始就只有一个写入者，不会有这个分歧）。
> **所以它只存在于这里和线上库里** —— 换台机器重建环境不会重现这个数。
>
> ★ 更一般地说：**删掉冗余副本不解决副本里的分歧，它只是让分歧不再可见。**
>   删之前对一次账，是这一步唯一需要的额外工作 ——
>   而它恰好是最容易跳过的一步，因为"删掉就好了"看起来就是终点。
>   这次的代价是：漂移被定格了 1 天，而**对账的证据（`product.stock` 那一列）已经不存在了**，
>   只能靠订单反推 —— 这也是为什么上面那段核对要写得这么细。

## 附：几个容易踩的坑（写给未来的自己）

- **`sql/mall.sql` 永远不能对已有数据的库跑**（见第三节）。
- **后端工作目录必须是 `mall-server/`**，否则 `./uploads` 会落到别处。
- **Redis 容器必须叫 `mall-redis`**，否则 6 个测试脚本清不了 key。
- **★ 脚本跑到一半机器休眠 → 一片 401，而且没有清理。** JWT 有效期是 120 分钟，
  脚本在开头登录一次就不管了；机器一睡（合盖、待机）再醒来，那个 token 早就过期，
  后半程全是 `401 登录已过期`。**这个坑的特征是「它只坏一个脚本」**：
  其余脚本是刚启动的、登录是新的，所以全绿 —— 于是看起来像是那一个脚本写错了。
  更坏的是脚本多半在断言失败处 `SystemExit`，**收尾的 `cleanup()` 不会跑**，
  库里留下它的商品和会员。**判据**：看失败是从哪一行开始的 ——
  如果前面几十条断言全过、从某个点起突然全部 401，那不是逻辑问题，是 token 死了。
  重跑一遍就好（脚本开头的 `cleanup()` 会先清掉上一次的残留）。
- **`mysql` 客户端在 Windows 上的命令行参数不吃带引号的 LIKE 模式。**
  `spec_json LIKE '%"黑色"'` 这种写法**恒不匹配**（返回 0 行、不报错），
  而 `LIKE '%黑色%'` 又能匹配 —— 于是这个坑只在「想精确匹配 `"值"` 这个形状」时才踩得到。
  **对策不是记住这个怪癖，而是：能不在 SQL 里拼字符串就别拼**
  （`tools/fixture-pay.py` 里是把行拉回来在 Python 里比，顺带还比子串匹配更严格）。
- **★★ 「按行的售后」对「按订单的状态」—— 里程碑 17 的中心张力，它在同一轮里出现了四次。**
  售后是**行级**事实（这一行退没退），而 `orders.status` 是**订单级**的。四个地方各撞一次：
  ① 库存归还的两条路径（仅退款在「货还在仓库」时还，退货退款在「货回到手里」时才还）；
  ② `orders.status = 5` 的聚合（行级事实要提升成订单级终态，否则管理员会把退过款的东西发出去）；
  ③ 评价资格（「这一行退过款没有」是行级的，不能拿 `orders.status` 代替）；
  ④ 运费的「全退才退」（退多少取决于**别的行**退成没退成）。
  **四次的解法是同一条**：*行级事实存在行上、聚合只在唯一一处、由唯一一条单调的条件 UPDATE 写入、
  并配一条能同时抓住漂移两个方向的断言。*
  ⚠️ 最容易走错的那一步是**「每完成一张售后就把订单置成已退款」** —— 部分退款时立刻错：
  退了一件整单变已退款，另一件用户**再也确认不了收货**。
- **`DEFAULT` 值会静默吃掉「忘记写的列」。** 给列配一个合理的 `DEFAULT` 是对的
  （判据见 `migration-14b`：这个 `0` 会不会被当成真实数据拿去比较和计算），
  但它的副作用是：**`INSERT` 的列清单里漏了这一列，语句照样成功。**
  里程碑 17 的 `orders.freight_amount` 就是实例 —— 漏写它的话运费永远是 0，
  而 `total_amount` 里已经含了运费，不报错、不警告。
  **对策不是不配 `DEFAULT`，而是给「本来该相等、漏写就不相等」的两个数配一条断言。**
- **改完 Java 一定要重启后端再跑测试。** `mvn spring-boot:run` 不会自动重编译，
  而症状是**全绿** —— 你测的是上一版代码。这是本项目里唯一一条「忘了就白干」的纪律。
- **`/tmp` 对 Windows 版 Python 不可见**（那是 Git Bash 的路径），脚本里要用真实路径。
- **时间格式是 `yyyy-MM-dd HH:mm:ss`**，前端 `new Date("2026-09-22 20:48:06")` 是非标准写法 ——
  Chrome 能解析，**Safari 直接给 `Invalid Date`**。前端要 `replace(' ', 'T')`。
- **金额在前端要 `.toFixed(2)`**：后端的 `228.70` 序列化成 JSON 数字会变成 `228.7`，
  不格式化就会出现「同一笔钱在购物车和收银台长得不一样」。
  ⚠️ **但别就地写 `.toFixed(2)`** —— 全工程只有 `mall-shop/src/utils/format.js` 一份实现，
  每一处金额显示都走它的 `formatAmount()`。
  就地再写一份，正是里程碑 14 花一整轮清掉的东西：那次清出**四份**逐字相同的副本，
  外加**四处**绕过它们、裸渲染的金额（`¥599` 和 `¥599.00` 并排出现在同一页上）。
  下一个想就地写的人会被 `sql/test-frontend-format.py` 拦住。
- **★★ 「同一个事实有两份实现，就一定会分岔」—— 这一条本轮又应验了一次，值得单独记下来。**
  里程碑 16 要给「筛父分类时含后代」算一个 id 集合（`selfAndDescendantIds`）。
  天真的写法是拿 `selectEnabledList()`（"启用中的分类"）来算后代 ——
  而**正确的来源是"全部分类"**（`selectIdAndParent()`）。
  两者的差别只在**一个被禁用的子分类**上，症状是：
  **它下面的商品，会从它那个【启用着】的父分类的筛选结果里消失。**
  分类禁用只该管住导航，不该把商品藏起来；而挑商品的人只会以为"这件没货了"，
  **没有任何一层会报错**。
  所以那个方法是这个问题的**唯一定义者**，两端都调它 ——
  如果管理端和用户端各写一遍，同一件商品在两个端上会给出两个数字
  （管理端 20 件、用户端 28 件），**而运营会先怀疑后台统计错了**，
  不会先怀疑这是两个不同的规则。
- **管理端列表的筛选参数是 `name`，用户端是 `keyword` —— 传错了【不报错】。**
  传错时后端当没看见，照样返回默认的第一页。于是
  **「搜到 0 条」和「搜错了字段」长得一模一样**。
  `tools/fixture-sku.py` 里传的就是 `keyword=`，它靠「列表按 id 倒序、新建的永远在第一页」
  侥幸对了 —— **靠侥幸成立的分支早晚会翻脸**。
  （`tools/fixture-price.py` 里刻意用 `name=`，并且在注释里写明了不靠侥幸。）
- **`el-input-number` 清空输入框得到的是 `null`，不是 `undefined`、也不是 `0`。**
  所以判断"商家没填这个值"要写 `x === null || x === undefined`（宽松判断也行），
  **只判 `undefined` 会在清空之后走进"填了"那个分支**，
  于是一个空输入框被当成一个合法的价格提交上去。
  （想让"清空"有别的含义是 `value-on-clear` 这个 prop 的事 —— 它的默认值就是 `null`。）
- **★ 一个 `computed` 返回 `Map`，在模板里写 `map[key]` —— 取到的永远是 `undefined`。**
  Map 的键**不是它的属性**，方括号访问不到它。
  这个坑的威力全在**它彻底静默**：编译通过、运行不报错、控制台一个字都没有，
  只是页面上那一格显示成"没有值"。
  本轮它让管理端 SKU 矩阵里**每一行**的毛利率都显示成「未设置」——
  而那恰好就是真没填成本价时的样子，
  于是「取不到」和「本来就没有」在界面上**长得一模一样**（这条判据本轮用了三次）。
  修法不是换个取值写法，是**别用 Map**：像 `specTextOf(row)` 那样把行传进一个函数里算。
- **★★ 「外部世界的记录」对「系统内部的状态」—— 里程碑 18 的中心张力。**
  物流轨迹是「外面发生了什么」，订单状态是「系统怎么判断这笔交易」。
  两者的关系是**一条单向的蕴含**：轨迹可以独立于订单状态存在
  （录了「运输中」而订单还是「已发货」，完全正常），
  但**订单状态绝不能被轨迹「猜」出来**。
  这一轮有四件事由这个不对称决定：
  ① 签收联动必须判 `status == SIGNED` 这个**码**，不能判「描述里有没有『已签收』三个字」——
     后者会在有人写「已签收失败，改约明天」的那天静默出错；
  ② 删除节点**不回退**订单状态（轨迹没了不代表事没发生）；
  ③ 承运商/单号是**自由文本**（外部世界的标识符，没有能穷举的表），
     而节点状态**必须是码**（前端要按它画颜色、它是联动的触发条件）；
  ④ 那条**只单向成立**的断言（见下）。
- **★★ 断言的方向由「这个条件是充要还是充分」决定，不由「写得全不全」决定。**
  里程碑 17 有一条**双向**断言：「订单 `status = 5`」⟺「每一行明细都有一张已退款的售后单」——
  两个方向都是真故障（反方向意味着管理员会把退过款的东西发出去）。
  里程碑 18 有一条**单向**断言：「有『已签收』节点」⟹「订单不是『已发货』」——
  **反方向刻意不写**，因为**订单已完成而没有签收节点是完全正常的**
  （用户自己点「确认收货」就是这个形态）。
  写成双向会让每一个走正常流程的订单都误报，然后被人加个条件掩盖掉，**断言从此失去意义**。
- **★ 补录是物流轨迹的【默认用法】，所以排序键不能是 `id`。**
  管理员白天忙、晚上把一天的节点一次性录进去 ——
  于是同一张订单的节点，`trace_time` 的顺序和 `id` 的顺序**相反**。
  按 `id DESC` 排的话，今天的「已揽收」会显示在昨天的「运输中」**上面**，
  而页面、代码、控制台**全都正常**（这是这一轮最安静的坑）。
  `ORDER BY trace_time DESC, id DESC` 里那个 `id DESC` 也不是装饰：
  两个节点被填了完全相同的 `trace_time` 时，只按时间排会返回**不确定的顺序**，
  每次查询都可能不一样 —— 断言随机红，然后被人用 `DISTINCT` 掩盖。
- **★ 同一条边、两个行动者、两条 SQL —— 里程碑 18 是第二次。**
  「已发货 → 已完成」这条边现在有两个行动者：买家点「确认收货」（`OrderMapper.markCompleted`，
  带 `member_id`）和管理员录「已签收」（`OrderAdminMapper.markCompletedByNo`，没有 `member_id`，
  身份靠 `AdminAuthInterceptor` 拦 `/api/admin/**`）。
  **第一次是「取消」**：用户主动取消 vs 定时任务超时取消。
  两条 SQL 的 `WHERE status = ?` 是**同一个闸门**，而 `OrderStatus` 的边表里两条都列了出来 ——
  漏列一条的后果是：下一个人改这条边时会只找到用户端那条，**管理端那条被静默漏掉**。
- **★ 「一个接口加了必填请求体」这种契约变更，在旧代码上【不会自己暴露】。**
  里程碑 18 把 `POST /admin/orders/{orderNo}/ship` 从「没有请求体」改成「必须带承运商 + 单号」。
  预期是四个测试脚本一起红，实际只有 `test-frontend-contract` 红了 ——
  因为**旧 Controller 上没有 `@RequestBody`，多传的 body 会被静默扔掉**，
  接口照常返回 200。
  所以「必填」这件事唯一的见证是**「不带 body 必须 400」**，
  它由新后端和 `sql/test-logistics.py` 的 B 组兑现。
  （同类：字段多一个少一个，后端测试往往照旧全绿，只有前端会安静地渲染出一片空白。）
- **★★ 同一个 `OrderVO` 有两条路，而它们「加字段」的方式不一样 —— 于是半路加漏了。**
  这是**跑端到端时才发现**的一个真漏洞，不是纸上的担心：
  - 订单**列表**走 MyBatis 的 `resultType="OrderVO"`，按列名自动映射 —— **加了列就自动有**；
  - 订单**详情**（和支付 / 取消 / 确认收货的响应）走 `OrderServiceImpl.toVO`，**手写逐字段搬**。

  里程碑 18 加 `logistics_company` / `tracking_no` 时，迁移、实体、VO 三处都改了，
  订单列表上单号显示得好好的，**而详情里它静默地没有** —— `non_null` 把整个 key 删掉，
  页面、构建、控制台**全都正常**。当时没有页面读详情的这两个字段，所以它一直没露出来；
  而**详情页恰恰是最可能顺手加一个「查看物流」入口的地方**。
  现在 `test-frontend-contract.py` 的 8b 节钉着「同一个 VO 的两条路不能说两套话」。
  **判据**：往 `OrderVO` 加的是**数据库里的列** → 只需在 `toVO` 搬一次；
  加的是**派生值**（`payDeadline` / `afterSaleDeadline`）→ `toVO` 和 `attachItems` **两处都要算**。
- **★ 给「挂在订单上的子表」建了一张，就要检查每一个「删订单」的地方。**
  `order_item` 是第一条（里程碑 8），`order_logistics` 是第二条（里程碑 18）。
  全库零外键是既定约定，所以**数据库不会替你拦住孤儿行** ——
  该拦的地方有三处：`sql/test-*.py` 的收尾 `cleanup()`、
  各脚本末尾的**孤儿检查**，以及 `tools/fixture-*.py --cleanup`。
  ⚠️ 这一轮漏的恰好是第三个：夹具**自己不发货、不录轨迹**，
  所以 `grep ship\|logistic tools/fixture-pay.py` 一处命中都没有，看起来完全不用改 ——
  但它建的订单**会在浏览器里被点出轨迹来**（管理员发货 + 录节点），
  清理时那些轨迹就成了孤儿（红的是 `test-logistics.py` 的孤儿检查）。
  **判据：不要 grep「这个脚本会不会用新表」，要问「它会不会删掉新表的父行」。**
